## 2. D가 이해해야 하는 핵심 계약

### A → D: 정상 대중교통 입력

- **정류장:** `stop_id`, `stop_name`, `stop_lat`, `stop_lon`
- **노선:** `route_id`, `route_type`, 노선명
- **운행편:** `trip_id`, `route_id`, `service_id`
- **정차 시각:** `trip_id`, `stop_id`, `stop_sequence`, `arrival_time`, `departure_time`
- **운행일:** `calendar.txt` 및/또는 `calendar_dates.txt`의 해당 운행일 정의
- **추가 확인:** 서비스 날짜, `agency_timezone`, 원천 정류장 ID와 GTFS `stop_id` 매핑, 누락·추정 시각의 구분, 시간표 버전

> 파일이 존재한다고 해서 모든 ID가 연결되거나 실제 시각이 맞는 것은 아니다. 기본 검사 통과와 경로 탐색 가능 여부는 별도로 판단한다.

### B → D: 임시 셔틀 운행 입력

- 검증을 마친 셔틀 운행안 ID 및 적용 시나리오 ID
- 셔틀 정류장별 **실제 계획 출발·도착시각** 또는 이를 표현한 GTFS
- 기존 일반 교통 GTFS와 겹치지 않는 노선·운행편·서비스 식별자
- 운행안 상태(`simulated`/확인된 실제 운행)와 시간표 버전
- 운영자 화면용 평가 결과·검증 결과: **계산 주체는 B, 화면 표시 주체는 D**

> 2026-11-08 기준 B Draft PR #6은 C 배분안에서 내부 `Trip`과 `schedule_status=compiled`를 생성하지만, `independently_verified=false`인 합성 M05 프로토타입이다. 병합 전이며 GTFS·M07 결과 전달 형식도 확정되지 않았으므로, 이 결과를 시민 안내·실제 운행·검증 완료로 취급하지 않는다.

### C → D: 운행안 선택·비교 입력

- 운행안 ID, 제목·상태, B가 평가한 결과를 참조할 연결 키
- 기준안·제안안의 구분 및 비교 기준 설명
- D는 최적화 점수나 수요 충족률을 임의로 재계산하지 않음

## 3. 서울시 엑셀로 확보된 정보와 부족한 정보

| 서울시 자료 열 | GTFS의 대응 필드 | 확인 사항 |
| --- | --- | --- |
| 위치정보 `NODE_ID` | `stops.stop_id` 후보 | GTFS ID로 사용할지 A와 합의 |
| 위치정보 `ARS_ID` | `stops.stop_code` 후보 | 앞자리 0이 사라지지 않도록 문자열 유지 |
| 위치정보 `정류소명` | `stops.stop_name` | 동일 이름의 여러 정류장 구분 |
| 위치정보 `Y좌표` / `X좌표` | `stop_lat` / `stop_lon` | 위도·경도 범위와 누락 확인 |
| 노선별 정류소 `ROUTE_ID`, `노선명` | `routes.route_id`, 노선명 후보 | 노선 방향·버전 구분 확인 |
| 노선별 정류소 `순번` | `stop_times.stop_sequence`의 입력 후보 | 동일 정류장 재방문도 보존 |
| 두 엑셀 모두 없음 | `trip_id`, `service_id`, 개별 정차시각 | **A가 별도 자료를 확보하거나 '합성/추정'임을 명시해야 함** |

위 대응은 **변환 후보**이며 최종 `contracts/`가 아니다. 서울시 두 엑셀만으로 특정 날짜·시각의 실제 시내버스 GTFS Schedule을 완성할 수 없다.

## 5. 현재 API 명세에서 이미 제안한 내용

| API | 요청/응답 설명 | 상태 |
| --- | --- | --- |
| `GET /api/v1/health` | 서비스 상태 | 경로만 정의 |
| `GET /api/v1/scenarios` | 조회 가능한 시나리오 목록 | 경로만 정의 |
| `POST /api/v1/journeys/search` | `plan_id`, **제안 `plan_revision`**, 출발·도착, ISO 8601 출발시각 → `journeys[]`, `legs[]` 등 | JSON 예제 있음·서버 미구현. 외부 revision 필드명은 미정 |
| `GET /api/v1/evaluations/{plan_id}?revision=1` | 특정 운행안 불변 버전의 평가·검증 결과 | D 제안·서버 미구현. M07 결과 형식 확인 후 확정 |

- `total_duration_sec` 등 내부 소요시간 단위는 **정수 초**.
- M00의 `plan_mode=simulation`은 합성·시뮬레이션 의미다. 실제 운행 확인 근거가 없다면 `operational` 또는 `confirmed`처럼 표현하지 않는다. `data_status`는 M00 최소 필드가 아니므로 새 계약으로 임의 확정하지 않는다.
- 문서의 `200 + journeys: []`는 **검색할 데이터가 준비된 상태에서 탐색했으나 경로가 없는 경우**에만 적절하다. 미완성 시간표·미지원 환승 때문에 못 찾은 경우는 '실제로 이동 불가'라고 판정하면 안 된다. 상세 상태 코드는 합의 필요.
- 아직 `arrival_at`, `waiting_time_sec`, `walking_time_sec`, `timetable_version` 등이 API 최종 필드로 확정되지 않았다. 필요성은 논의하되 계약 수정은 별도 합의를 거친다.
