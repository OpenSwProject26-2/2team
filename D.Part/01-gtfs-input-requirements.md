# D 파트 1~2일 차: GTFS 입력 요구사항

> 상태: **구현을 위한 입력 명세 초안** | 담당: D (`routing/`) | 기준: 2026-11-06
>
> 이 문서는 **D가 어떤 데이터를 받아 경로를 검색할지** 정의한다. GTFS 파일 자체의 생성은 A/B 담당이며, D는 이를 입력으로 읽는 경로 탐색 서비스를 담당한다. 이 문서에서 제시하는 연계 형식은 실제 `contracts/` 모델이 생기면 그에 맞춰 조정한다.

## 1. 목적과 범위

시민이 출발 정류장·도착 정류장·출발 시각을 입력하면, **버스 파업으로 중단된 노선을 제외하고 임시 셔틀을 반영한 이동 경로**를 조회할 수 있어야 한다. 이를 위해 D의 경로 탐색기에는 아래 세 종류의 입력이 필요하다.

| 입력 | 제공 예정 | 내용 | D에서의 용도 |
| --- | --- | --- | --- |
| 평상시 교통 GTFS | A (`gtfs/`) | 버스·도시철도 정류장, 노선, 운행 시각 | 기본 대중교통망 구성 |
| 파업 적용 정보 | 팀 공통으로 정의 필요 | 운행 중단 노선, 적용 시나리오 및 운행일 | 파업 중 노선 제외 |
| 임시 셔틀 GTFS | B (`sim/`) | 셔틀 노선과 운행 일정을 GTFS로 표현 | 대체 경로 추가 |

**이번 단계에서 하는 일:** 입력 파일 목록·필수 정보·검증 기준 정의. **이번 단계에서 하지 않는 일:** 실제 서울 교통망 수집, GTFS 생성, OTP/r5py 설치·경로 계산 구현(3~5일 차부터).

## 2. GTFS Schedule 입력 목록

공식 규격: https://gtfs.org/documentation/schedule/reference/

| 파일 | 필요한 대표 필드 | 사용 이유 | 요구 여부 |
| --- | --- | --- | --- |
| `agency.txt` | `agency_name`, `agency_url`, `agency_timezone` | 운행 주체·시간대 | 필수 |
| `stops.txt` | `stop_id`, `stop_name`, `stop_lat`, `stop_lon` | 위치·정류장 선택 | 정류장 기반 경로 검색에 필수 |
| `routes.txt` | `route_id`, `route_type`, `route_short_name` 또는 `route_long_name` | 버스·지하철 노선 식별 | 필수 |
| `trips.txt` | `route_id`, `service_id`, `trip_id` | 노선의 개별 운행 | 필수 |
| `stop_times.txt` | `trip_id`, `stop_id`, `stop_sequence`, `arrival_time`, `departure_time` | 정류장별 도착·출발 시간 | 필수 파일, 개별 시간 필드에는 조건부 규칙 존재 |
| `calendar.txt` / `calendar_dates.txt` | `service_id`, 운행 날짜 | 운행 가능한 날짜 판단 | 두 파일의 조건부 필수 규칙 준수 |
| `shapes.txt` | `shape_id`, `shape_pt_lat`, `shape_pt_lon`, `shape_pt_sequence` | 지도에 실제 노선 형태 표시 | 선택(지도 개발 시 권장) |
| `transfers.txt` | `from_stop_id`, `to_stop_id`, `transfer_type` | 환승 제약 반영 | 선택 |

GTFS는 텍스트 확장자의 CSV를 폴더 또는 ZIP으로 제공할 수 있다. 실제 입력 위치·전달 단위는 아직 정해지지 않았으므로 **임의의 프로젝트 폴더를 확정하지 않는다.**

## 3. D에서 사용할 공통 입력 규칙

### 3.1 식별자

- 화면과 API에서는 `stop_id`를 사용해 출발지·도착지를 구별한다.
- GTFS 내부 `route_id`, `trip_id`, `service_id`는 서로 참조되어야 한다.
- A의 원천 데이터에 같은 `ROUTE_ID`의 여러 버전·방향이 있을 수 있으므로 정제 단계의 식별 기준을 확인한다. 원천 `ROUTE_ID`와 GTFS `route_id`가 같다고 가정하지 않는다.
- A의 일반 노선과 B의 셔틀 노선을 합칠 때 ID가 충돌하면 안 된다(예: 셔틀용 접두사 부여, 구체적 규칙은 후속 확정).

### 3.2 좌표·시간

- 좌표는 정제된 위도 `lat`, 경도 `lon` 또는 GTFS `stop_lat`, `stop_lon`을 사용한다. 원천 `DH`의 `BSST_LAT`/`BSST_LON`은 팀 문서에 축과 DDMM 형식 주의사항이 있으므로 직접 사용하지 않는다.
- 서비스 시간대는 GTFS의 `agency_timezone`을 따른다(서울 데이터의 경우 `Asia/Seoul`인지 확인).
- 내부 시간 계산은 **초 단위 정수(`int`)**로 통일한다.
- GTFS에는 `24:10:00`처럼 운행일 기준 24시간을 넘는 시각이 가능하므로 자정 넘김을 보존한다.

### 3.3 파업 상태 및 셔틀 반영

아래 값은 **D가 요구하는 개념적 입력**이며, 실제 필드명은 확정 전이다.

```json
{
  "scenario_id": "DEMO_STRIKE_SHUTTLE",
  "service_date": "2026-11-09",
  "suspended_route_ids": ["DEMO_BUS_1"],
  "shuttle_feed_id": "DEMO_SHUTTLE_FEED"
}
```

- 파업 시나리오에서는 중단 노선이 검색 결과에 나타나지 않아야 한다.
- `shuttle_feed_id`는 B가 만든 **합성 운행안**을 연결하기 위한 예시 필드다. 실제 운영이 확인되지 않았으면 `simulated`로 표시한다.
- 같은 조건에서 셔틀 GTFS를 적용하면 셔틀을 이용하는 대체 경로가 검색 후보에 포함될 수 있어야 한다.

## 4. 수령한 데이터에 대한 검증 기준

- [ ] GTFS 파일이 UTF-8 텍스트 CSV로 열리고 필수 파일이 존재한다.
- [ ] `stop_times.trip_id`가 `trips.trip_id`를 참조한다.
- [ ] `trips.route_id`가 `routes.route_id`를 참조한다.
- [ ] 정류장 좌표가 위도·경도 범위에 들어가고, 표시용 위치가 정상이다.
- [ ] 검색 날짜가 `calendar`/`calendar_dates`의 실제 운행일과 맞는다.
- [ ] 정류장·노선·운행 ID가 통합 데이터에서 충돌하지 않는다.
- [ ] 파업 중단 노선이 탐색용 데이터에서 제외된다.
- [ ] 테스트 데이터는 원시 교통카드·카드 식별자(`TRCR_ID`)를 포함하지 않는다.

## 5. 3~5일 차 테스트 예제 (후속 작업 기준)

**합성 시나리오:** 정류장 A–B 간 일반 버스 1개와 셔틀 1개가 있는 작은 GTFS.

| 테스트 | 입력 | 기대 결과 |
| --- | --- | --- |
| 정상 | 일반 버스 운행 | A → B 경로 1개 이상 |
| 파업 | 일반 버스 중단 | 중단된 버스를 이용한 경로가 검색되지 않음 |
| 파업+셔틀 | 일반 버스 중단, 셔틀 추가 | 셔틀을 포함한 경로가 검색 가능 |
| 잘못된 ID | 미존재 `stop_id` | 명확한 오류 반환 |

### 이번 단계 완료 기준

GTFS 필수 입력 목록, 입력 제공 주체, 파업/셔틀 결합 방식, 좌표·시간·식별자 규칙, 수령 후 검증 체크리스트를 **문서로 작성해 GitHub에 기록했다면 1~2일 차 GTFS 명세 작성은 완료**다. 실제 데이터와 엔진 연동은 후속 단계다.

## 6. 현재 미확정된 연계 사항

- A의 GTFS 전달 경로/생성 방법과 `stop_id` 매핑
- B의 셔틀 GTFS 제공 방식과 운행안 식별자
- 실제 파업 중단 노선 목록의 생성 주체 및 데이터 구조
- 경로 엔진(OTP 또는 r5py) 선택과 배포 방식

위 사항은 **아직 존재하지 않는 기능을 완성된 것처럼 표시하지 않기 위해** 기록한 것이다. 데이터를 임의 생성해 실제라고 표시하지 않는다.
