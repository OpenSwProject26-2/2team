## 동일성

- 같은 규모의 모든 실행(P3 전·후, batch·stream)에서 `metrics.json` sha256과 사건 수가 같다
  (1만 `badffad358b30095`/117,127, 10만 `f0194e333047bc73`/384,015, 90만 `58ca07e124232691`/2,102,112).
- 단위 테스트: golden 사건 로그 13개가 batch·stream 모두 바이트 동일, 스트림 RunInputs checksum이
  `digest(asdict(...))`와 동일, 스트리밍과 배치의 지표 보고 동일.

## 해석과 한계

- 감소 원인(코드 구조상): 승객당 3개·방문당 3개 선적재 사건과 closure 제거(정렬 스트림), 처리된 키 폐기,
  checksum의 승객 전체 dict/JSON 복사 제거, `__slots__`. 측정 감소분을 원인별로 분리하지는 않았다.
- stream은 90만에서 batch보다 peak RSS가 약 75 MiB 낮지만 run 단계는 결과 CSV 쓰기가 들어가 더 길다.
- 여전히 O(N): 입력 `Passenger` 튜플, R5 생성, 대기열은 N에 비례한다. cohort 압축은 범위 외로 두었다.
- 기록 주의: P3 전 90만 r1의 `dirty=True`는 실행 종료 시점에 git 상태를 읽는 동안 엔진을 수정 중이었기
  때문이다. 코드는 수정 전에 로드됐고 지표 해시가 r2·r3(clean)와 같다. env_manifest는 실행 시작 시점에
  기록하도록 후속 커밋에서 고친다.
- 단일 머신·단일 망·단일 seed 결과이며 독립 검증(M07) 전 잠정치다. 실제 운행 성능을 뜻하지 않는다.
