# 버스 파업 셔틀 시뮬레이터(M05) + 독립 검증기

## 맥락
- 서울 시내버스 파업 때 자치구 임시 셔틀 운행안을 같은 조건에서 채점·비교하는 대학 공개SW 팀 프로젝트(Python).
- 비교 대상: 지자체 운행안, 범용 AI 운행안, 우리 최적화 운행안. 핵심은 같은 승객 입력·같은 시뮬레이터·같은 검증기.
- 1차 범위: 구로구, 평일 06~10시. 수요는 2026-10-26~30(개발), 평가는 2026-11-02~06 공개 실측.
- 파이프라인: 1 수요 점(M03) → 2 수요 벡터(M03) → 3 파업 잔여 수요(M03) → 4 노선 후보 생성(M04, C) → 5 대수·예산 배분(M04, C: 근사 평가로 탐색 후 유망 후보를 시뮬레이터로 재평가) → 시뮬레이션+검증(M05·M07, B).
- B의 산출물: 차량별 출발표, 수송 실행(이벤트 로그), 검증 결과, 지표, 셔틀 GTFS 내보내기.

## 입력 (M00 v0.1 계약)
- Scenario: scenario_id, service_date, timezone(Asia/Seoul), network_snapshot_id, demand_profile_id, strike_route_ids, fleet(차량 ID·정원·차급·가용 시각·초기 위치·종료 조건, 인가대수와 가용대수 구분), operating_window, policy(최대 누적 대기, 최대 총 이동시간, 허용 환승, 승객 발생 분포, 정차·회차 가정, 미확인 연결 처리).
- RunInputs: input_bundle_id, scenario_id, seed, arrival_realization_uri, travel_time_realization_uri, checksum. 비교 실험은 같은 RunInputs를 재사용하고, seed만으로 같은 입력이라 주장하지 않는다.
- ServicePlan: (plan_id, revision) 불변, routes·vehicle_duties·trips는 모듈 소유. 지자체안은 노선+대수만 있고 시간표가 없는 경우가 많다.
- SimulationResult(출력): run_id, plan_id, plan_revision, input_bundle_id, metrics_uri, event_log_uri, config_hash.

## 데이터 사실
- 수요 벡터: access(정류장→지하철역), egress(역→정류장), 시간대별 유량(소수 포함). 06~10시 첫 승차 기준.
- 이동시간: TPSS 노선 구간 속도(평일·시간대별), 버스 GTFS 구간 시간 근사. 도로망은 버스 GTFS 연속 정류장 구간.
- 비파업 노선(마을버스 등) 배차간격·운행횟수 있음.
- 승객은 노선·정류장을 안다고 가정. 이동 포기·수단 전환은 반영하지 않음.

## 설계 원칙
1. 결정론: 같은 RunInputs + 같은 ServicePlan이면 이벤트 로그가 바이트 단위로 같다. 시뮬레이터 안에서 난수 금지. 동시각 이벤트 처리 순서를 명시.
2. 공정성: 운행안 종류에 따라 다른 코드 경로 금지. 시간표 없는 안을 시간표로 바꾸는 규칙도 모든 안에 동일.
3. 검증 가능성: 독립 검증기는 시뮬레이터 코드를 import하지 않고 입력+로그만으로 불변식 재계산.
4. 설명 가능성: 못 탄 승객마다 원인(노선이 정류장에 안 옴 / 목적 역으로 안 감 / 만차 / 대기 한도 초과).
5. 속도: 5단계가 노선별 대수 곡선 S(n)을 위해 반복 실행. 구로 규모(승객 수만 명, 차량 수십 대) 1회 실행 목표 시간 제시.

## 설계 항목 (각각 결정 + 이유 + 의사코드, 버린 대안은 한 줄씩)
1. 시간표 생성기: 노선+대수 n+운영시간+구간 시간 → 차량별 trip·duty. 순환시간, 배차간격, 첫차·오프셋, 차고지 공차, 회차·휴식, 종료. 피더형(편도+회송)·순환형·두 역 연결형.
2. 승객 발생 실현기: 소수 유량 → 정수 승객+도착 시각(포아송/균등/체계적 반올림 중 선택), seed·체크섬, 승객 필드(출발 정류장, 허용 목적지 집합, 도착 시각, 최대 대기), egress 승객 처리.
3. 이벤트 모델: 이벤트 종류, 우선순위 큐 정렬 키와 동시각 순서, 정류장 처리 순서(하차→승차→정차→출발), 정차시간 모델(기본+1인당), 시간대별 구간 시간 조회.
4. 탑승 규칙: 목적지 가는 첫 차량, 여러 노선이 서는 정류장, FIFO, 만차로 남겨짐 기록, 좌석/입석 정원, v1 환승 허용 범위.
5. 비파업 노선: 시뮬레이터 안에서 차량으로 돌릴지, 3단계 전처리로 끝낼지와 근거, 확장 지점.
6. 출력: 이벤트 로그 스키마(필드·형식·정렬), 지표(수송 인원, 충족률, 대기 분포, 차내·총 이동시간, 차량별 km·시간, 대당 수송, trip별 재차율, 미충족 원인별·정류장별), 셔틀 GTFS(routes·trips·stop_times·calendar), config_hash 범위.
7. 대수 곡선 지원: 노선별 S(n) 실행 방식, 정류장 공유 시 처리, C의 근사 평가와 비교·보정 방법.
8. 독립 검증기 불변식: 인원 보존(발생 = 수송 + 포기 + 종료 시 대기), 정원 초과 없음, 차량 일정 중복 없음, 시간 단조성, 승차 전 도착, 하차 정류장이 승차 이후, 구간 시간이 realization과 일치, 운영시간 준수, 위반 리포트 형식.
9. 테스트: 손계산 최소 시나리오들(예: 정류장 3·차량 1·승객 5)과 기대 결과 표, 결정론 테스트, 노선+대수만 있는 지자체안 재현 테스트.
10. 모듈 구조: src/busstrike/sim/, 검증기는 src/busstrike/evaluation/, 파일별 책임, 공개 함수 시그니처.
11. 미확정 결정 D02(평가 단위: 버스 한 구간/전체 통행), D03(가용 차량·초기 위치), D06(환승·도보·정상 수단 범위), D07(최대 대기·총 이동시간): 시뮬레이터 관점 권장값과 이유.
