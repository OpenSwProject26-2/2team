# 운영 종료 규칙 비교 — 구로 실험 묶음(10/26~30) × 스모크 안

> 이 문서는 `experiments/guro_exp/report_service_end_rule.py`가 두 벌의 실행 결과(`runs.json`과 실행별 `metrics.json`·`timetable.json`·`passenger_outcomes.csv`·`network.json`·`verifier_report.json`)를 읽어 만든다. 숫자를 손으로 고치지 않는다. 실행 원본은 저장소 밖에 있고 커밋하지 않는다.

## 요약

- 실행 40회 × 규칙 2개. M07 검증 pass: 현행 규칙 40/40, 새 규칙 40/40 (`--max-recompute 200000`).
- service_end 인원(40회 평균): 132.4명 → 18.2명. 충족률(40회 평균): 5.8% → 6.7%.
- 순환이 가장 긴 노선 r2(주기 74.3분, 11대 조건)의 마지막 영업 출발: 08:29:02 → 09:42:54.
- 새 규칙에서 가장 늦은 차량 복귀는 10:48:02이고, 모든 운행편 복귀가 차량 가용 종료 안이다(예). 가장 늦은 운행편 시작은 09:56:01(운영창 끝 10:00:00보다 이르다: 예).
- 돌린 안은 **스모크 안 하나뿐**이고 비교안이 아니다. 규칙이 운행안 순위를 어떻게 바꾸는지는 이 실행으로 보이지 못한다. 노선 길이에 따른 편향이 줄어드는지는 §4·§5의 노선별 값으로만 본다.

## 1. 규칙과 실행 조건

| 규칙 | `policy.service_end_rule` | 순환을 넣는 조건 |
|---|---|---|
| 현행 규칙 | `cycle_within_window`(필드 없음 = 기본값) | 순환 전체(영업 + 회차 + 공차 복귀)가 min(운영창 끝, 차량 가용 종료) 안에 끝남 |
| 새 규칙 | `start_within_window_return_by_available` | 순환 시작(첫 영업 leg 출발) < 운영창 끝, 순환 전체 ≤ 그 차량의 `available_end_s` |

- 입력 묶음: `guro_0610_2.zip` — README 제목 "구로구 06~10시 시뮬레이터 입력 묶음 v3 (M05 6단계 · M07 형식)". 묶음 20개 = 변형 4개 × 날짜 5일(10/26, 10/27, 10/28, 10/29, 10/30), 차량 조건 11대, 13대.
- 작업 지시에는 `guro_0610.zip`이라고 적혀 있었으나, 지시한 사람이 `guro_0610_2.zip`(v3, 망 `guro-buf2km-0610-v2`)이 맞다고 확인했다. 파일 이름은 그쪽에서 정리한다. 지시가 인용한 숫자(순환 74분 노선 막차 08:29, service_end 약 18%)도 이 묶음의 실행 결과다.
- 테스트 묶음(`guro_0610_test`)은 열지도 돌리지도 않았다.
- 새 규칙 입력: 원본 묶음의 사본에 `policy.service_end_rule`만 더했다(`experiments/guro_exp/make_rule_bundles.py`). 그 때문에 `run_inputs`의 `scenario_sha256`·`checksum` 두 값만 다시 계산했다. 수요·구간시간·seed·`input_bundle_id`는 원본과 같다(ID 집합 같음: 예). 원본 묶음 파일은 바꾸지 않았다.
- 엔진: 실행 시점 브랜치 `fix/service-end-rule`, 기준 커밋 `324ae0c`(main), 추적 파일 변경 True. 그 변경은 커밋 `03990af`(`fix/service-end-rule`)의 `src/`와 같다(보고서 작성 시점 작업 트리 `src/` = 그 커밋의 `src/`, 바뀐 src 파일 5개의 마지막 수정이 두 실행의 시작보다 이르다). 엔진 기록 env 종류 1개(busstrike-sim/0.2.0).
- 정책(전 실행 같음, 규칙 필드만 다름): 대기 한도 1200초, 총 이동 한도 3600초, 정차 10초, 회차 180초.
- 운영창 끝 10:00:00, 차량 가용 종료 11:00:00, 관측 끝 drain 11:00:00(= 운영창 끝 + 총 이동 한도). 가용 종료가 drain보다 늦지 않아 새 규칙의 모든 방문이 관측 안에 든다.

**새 규칙의 가정** (결과 해석 전에 볼 것)

- 차량 가용 종료 11:00:00은 **시나리오 가정이다(실측 아님).** 운전자 근무시간·차량 반납 시각은 확인하지 않았다.
- 10:00 이후 구간시간은 **09시 값을 쓴다.** 묶음에 10시 프로필이 없어서다(구간시간 표의 마지막 시간대가 09:00, simulator.md 가정 A28). 10시 프로필은 묶음 쪽에서 추가할 예정이다.

## 6. 해석과 한계

- 새 규칙은 **차량을 가용 종료(11:00)까지 쓴다**는 가정이다. 운전자 근무시간·차량 반납 시각은 확인되지 않았다(§1 가정). ADR-001은 "복귀 완료가 운영 종료를 넘는 운행은 생성하지 않는다"(현행 규칙)를 적고 있다. 비교 실험을 새 규칙으로 돌릴지는 팀 결정이 필요하다(`docs/adr/ADR-002.md` 초안, `fix/service-end-rule` 브랜치). 코드의 기본값은 현행 규칙 그대로다.
- 승객 발생은 두 규칙 모두 06:00~10:00 안이다. 새 규칙에서 남는 service_end는 마지막으로 10:00 전에 출발한 차가 그 정류장을 지난 뒤 온 승객과, 대기 한도 안에 차가 오지 않는 승객이다.
- 새 규칙에서 M2 wait가 조금 는다. 사유 우선순위가 no_connection → service_end → journey → wait라서, 현행 규칙에서 service_end였던 승객 중 새로 생긴 늦은 운행편이 대기 한도(1200초) 뒤에 오는 승객은 wait로 옮겨 간다. service_end 감소분이 모두 충족으로 바뀐 것은 아니다(§3의 served·wait 차이).
- 10:00 뒤 구간시간은 09:00 시간대 값이다(관측값이 아니다, §1 가정). 10시대 혼잡이 다르면 10:00 뒤 도착 시각이 달라진다. 묶음에 10시 프로필이 들어오면 새 규칙 실행을 다시 돌린다.
- 운행안이 하나(스모크 안)라 **순위 변화는 보이지 못한다.** 다만 현행 규칙은 순환이 긴 노선일수록 운영시간 후반을 더 많이 비우고(§4), 새 규칙은 그 차이를 줄인다. 비교안이 생기면 두 규칙으로 같이 돌려 순위가 바뀌는지 봐야 한다.
- C의 근사 평가(`busstrike.planning`)는 현행 규칙(`departure + cycle <= end`)을 쓴다. 새 규칙 실행과 C 근사는 시간표가 같지 않다(simulator.md §1.3). 이번 작업은 planning 쪽을 바꾸지 않았다.
- M6 거리는 직선거리 기준이다. 새 규칙에서 늘어난 거리는 10:00 뒤 운행분이다.
