# routegen v1 설정 × v4 구 묶음 — 구로 v3 대비, 4개 구, 실험 → 테스트

입력은 `region_bundles_0610_v4.zip`(구로·동작·강서·강동 × 실험 10/26~30 · 테스트 11/02~06)이다. 이 문서의 숫자는 모두 `experiments/guro_routegen/make_report_v4.py`가 결과 파일에서 계산했다.

- 후보 생성·배분은 **실험 묶음에서만** 했고, 테스트 묶음에는 그 안(plan.json)을 고치지 않고 돌렸다. 그래서 테스트 충족률은 표본 밖 성능이다.
- 설정은 v1 기본 조건(`base`) 그대로다: τ 0.2, 군집 상한 3, R 3km, L_max 20·30분, N_max 8, 우회율 1.6, 섹터 2·3·4, 피더 seed 상위 15, Jaccard 0.8, 국소 탐색·초기해 3개. 대수만 묶음 README 값을 쓴다.
- 실행 640회 중 변환기 → M05 → M07(`--max-recompute 200000`) pass **640회**. 미검증 항목: V12,V15,V16 (이전 보고서들과 같은 항목).
- 충족률 = M1 served ÷ M1 total(그날 잔여 수요), 5일 평균 (최소–최대).

1. **수요가 고르게 흩어져 있다.** 1위 역 비중 9.4%(다른 세 구 16.9%–19.8%). 한 역에 노선을 모아 얻는 이득이 작다.
2. **큰 역 일부에 닿는 후보가 거의 없다.** 상위 6개 역 중 염창(9.2%, 풀 덮개 0), 화곡(8.6%, 풀 덮개 95), 등촌(8.3%, 풀 덮개 44)은 후보 풀 전체가 덮을 수 있는 수요가 그 역 수요의 10%도 안 된다. 합하면 잔여 수요의 26.1%이다.
   - 염창: 역 access 지정 정류장 `115000002`에서 망으로 닿는 정류장이 8개뿐이다(상위 10개 역의 다른 정류장은 최대 747개, 망 정류장 916개). 그래서 제약을 지키는 단일 seed 노선 20개(seed 수요 652)가 모두 변환기 공차 복귀 검사(`RETURN`, 끝 정류장 → 첫 정류장 경로 없음)에서 떨어진다. 2km 버퍼 망 가장자리의 막다른 구간으로 보이며 **망 데이터 쪽 확인이 필요하다**(routegen 설정으로는 풀 수 없다).
   - 화곡·등촌·우장산: access seed 중 제약을 지키는 것이 10% 이하다. 역 정류장까지 망 위 최단경로가 직선거리에 비해 크게 돌아서 대부분이 우회율·N_max·L_max에 동시에 걸린다(위 표 '주된 거절').
3. **차량·좌석은 제약이 아니다.** 대기 초과 20대 25명, 40대 25명, 좌석 부족 거절 20대 57회, 40대 57회. 미충족의 대부분은 노선이 없는 OD다.
4. **생성 후보가 피더 후보에 더하는 것이 거의 없다.** 우리 풀의 덮개 2,662명은 피더 풀 2,625명보다 +37명뿐이다(다른 구 +208~+563명). 그래서 같은 배분기에서 두 안이 거의 같은 노선을 고른다.
5. **배분만 바꿔 얻을 수 있는 상한**: 어떤 배분도 후보 풀 덮개 2,662명(19.3%)을 넘지 못한다. 지금 덮개는 20대 1,721명(12.5%), 40대 2,171명(15.8%)이다. 지금 배분이 그 대수에서 최적에 얼마나 가까운지는 확인하지 않았다(정확한 배분 최적화 미적용). 상한 자체가 낮으므로 개선의 큰 몫은 배분보다 후보(망 연결·역 지정 정류장) 쪽에 있다.

## 7. 코드에서 고친 곳 (`feat/candidate-gen`, 커밋 8454b9b)

- `routegen/data.py` `check_root`: 구로 망 ID(`guro-buf2km-0610-v2`)·v3 README 문구·실험 날짜 고정 → 망 ID 형식 `<구>-buf2km-0610-v2`(망 폴더·묶음 전부 같은 ID), README 주간 문구 v3·v4 둘 다, `split`(exp 10/26~30 · test 11/02~06). README에서 구 이름과 대수를 읽어 기본값으로 쓴다. 후보 생성기는 `split=exp`로만 묶음을 확인하므로, 테스트 묶음(11/02~06)을 `--root`로 주어 후보를 만들려 하면 확인 단계에서 멈춘다.
- `routegen/data.py` `check_bundles`: `scenario_f11.json` 고정 → 실행 대수의 시나리오(동작·강서 20·40, 강동 35·70에는 f11이 없다).
- `routegen/__main__.py`: `--fleets` 기본 11,13 → README 대수. `home_gu`(cross_gu 표시) 구로구 고정 → README 구 이름(`--home-gu`로 바꿀 수 있음).
- `experiments/guro_routegen/run_sims.py`: `--eval-root` — 실험 주간 안을 테스트 묶음에 그대로 돌린다(망 ID·구 같은지 확인, 결과는 `runs_test/`).
- 고치지 않은 것: ① `gg_reach`는 처음부터 행(쌍 × 날짜 × 시간) 단위로 읽고 거른다 — 쌍 단위 캐시가 없다. 단위 테스트 `HourlyReachTest`를 더했고, 실험·테스트 묶음 160개 전부 잔여 수요가 demand_bins와 같다(§1). ② 수요 비율은 routegen이 계산하지 않고 묶음 `demand_flows`를 그대로 읽으므로 고칠 곳이 없다. ③ 06~09시는 `HOURS = (6, 7, 8, 9)`로 이미 같다.
- **서울 전체 벡터 입력은 지금 브랜치가 읽을 수 없다.** 이 브랜치의 routegen은 구 묶음 형식(`network/` + `demand/demand_flows.csv.gz` + `bundles/<변형>_<날짜>/scenario_f*.json`)만 읽는다. 서울 전체 입력(`seoul_routegen_inputs_0610_v4`)은 수요가 `demand/exp/`·`demand/test/` 아래 `access_vectors_seoul.csv.gz`·`egress_vectors_seoul.csv.gz`로 나뉘어 있고, 열도 다르다(`kind`·`stop_id`·`station_stop_id`·`in_network` 없음, `stop`·`station`·`f0`·`f2`·`f2g`·`gg_runs_h` 있음). 시나리오(`bundles/`)도 없다. 그래서 `demand/exp`·`demand/test` 경로 분리는 이 브랜치 코드에 영향이 없고, 서울 전체로 돌리려면 이 형식을 읽는 로더와 시나리오 생성이 새로 필요하다(이번에는 만들지 않았다).
- 회귀 확인: 바꾼 코드로 v3 구로 묶음(`--fleets 11,13`)을 다시 돌린 plan.json 16개가 v1 기본 조건과 바이트 단위로 같다. v4 4개 구도 두 번 돌린 plan 64개가 같다. 전체 단위 테스트 통과.
