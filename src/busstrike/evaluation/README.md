# M07 지표·독립 검증·지자체안 비교

## M05 독립 검증기

`docs/verifier_spec.md`(엔진 브랜치 `feat/5-simulation-core`, 명세 커밋 `ca643f6`)의 V1–V17을
구현한다. 검증 통과 전 M05 수치는 모두 "독립 검증 전 잠정"이다.

```sh
pip install -e .
python -m busstrike.evaluation.verify <실행 결과 폴더>
```

| 옵션 | 뜻 |
| --- | --- |
| `--scenario DIR` | 시나리오 폴더. 생략하면 run 옆·상위에서 찾는다 |
| `--out PATH` | 보고서 경로. 기본 `<run>/verifier_report.json`, `-`는 표준출력 |
| `--max-recompute N` | 재계산 oracle 승객 상한 (기본 10,000, 명세 §4) |
| `--scan {full,index}` | 승차 자격 탐색 방식. `full`이 명세 문장 그대로다 |
| `--quiet` | 요약 표를 찍지 않는다 |

종료 코드: 0 통과 · 1 검사 실패 · 2 입력 오류.

`--write-realization` 없이 실행한 결과도 검증한다. `realization.jsonl`이 없으면
`demand_bins.csv`와 seed로 발생을 다시 만들어 `passenger_outcomes.csv`와 비교한다
(명세 §2의 (b) 경로이며 독립성이 더 높다). 다만 checksum 대조는 하지 못한다.

### 보고서

`verifier_report.json`에 검사 ID별 상태·검사 대상 수·위반 수·앞 20건 위반 예, 입력 파일
sha256, 검증기 커밋·작성자, 엔진 커밋을 담는다. 엔진 커밋은 `measurement.json`의 기록을
**인용**한 값이며 검증기가 확인한 값이 아니다.

`pass`와 `fully_verified`를 따로 둔다.

- `pass` — 실패한 검사가 하나도 없다. 하나라도 실패하면 `false`다.
- `fully_verified` — 실패도 미실행도 미검증도 없다. V16이 영구히 `not_verified`이므로
  현재 구조에서는 **항상 `false`**다. `pass=true`를 "전부 검증했다"로 읽으면 안 된다.

### 독립성 (명세 §1)

| 규칙 | 지키는 방법 |
| --- | --- |
| 코드 분리 | 이 패키지는 `sim`·`opt`·`busstrike.sim`·`busstrike.planning`을 import하지 않는다. 엔진 함수·자료구조·상수를 복사하지 않는다 |
| 입력 경로 | 파일만 읽는다(`inputs.py`). 엔진을 호출해 얻은 값을 정답으로 쓰지 않는다 |
| 정답 출처 | 손계산 fixture(`tests/evaluation/fixtures/handcalc/`) · 검증기 자체 재계산 · 불변조건 |
| 작성자 분리 | 엔진(`sim/engine.py`·`dispatcher.py`·`metrics.py`·`arrivals.py`) 커밋 작성자가 아닌 사람이 작성 |
| 실패 처리 | 하나라도 실패하면 보고서 `pass=false`. 부분 통과를 "검증됨"으로 쓰지 않는다 |

정적 검사: `tests/evaluation/test_import_independence.py`. 깨끗한 하위 프로세스에서
검증기만 import해 엔진 모듈이 적재되지 않는 것까지 확인한다.

외부 패키지를 쓰지 않는다. 표준 라이브러리만 쓴다.

## 방법론 — 무엇을 어떻게 검증하는가

시뮬레이터가 "919명이 도착했다"고 말할 때, 그 말이 맞는지 **엔진에게 되묻지 않는다.**
엔진에 버그가 있으면 엔진도 모르기 때문이다. 대신 세 방향에서 따로 확인한다.

| 방법 | 묻는 것 | 정답의 출처 | 담당 |
| --- | --- | --- | --- |
| **① 불변조건** | 로그가 스스로 모순되지 않는가 | 물리적으로 불가능한 일 | V2–V5, V8 |
| **② 재계산** | 같은 입력에서 같은 결과가 나오는가 | 검증기가 처음부터 다시 돌린 결과 | V1, V6, V7, V9–V14 |
| **③ 손계산 대조** | 사람이 손으로 푼 답과 맞는가 | 명세 §5 표를 사람이 옮긴 파일 | 테스트 |

세 가지가 서로를 보완한다. ①은 입력 없이도 되지만 "조리 있게 틀린" 로그는 통과시킨다.
②는 강력하지만 검증기가 같은 오해를 하면 같이 틀린다. ③은 그 오해를 잡지만 작은 예제에만
쓸 수 있다.

### ① 불변조건 — 로그 자체의 모순

승객 수를 몰라도 판정할 수 있는 것들이다.

- 안 탄 사람이 내릴 수 없다 · 한 사람이 두 차에 동시에 탈 수 없다 (V4)
- 정원 2인 차에 3명이 탈 수 없다 · 사건으로 센 인원과 기록된 인원이 달라서는 안 된다 (V5)
- 시간표에 없는 정류장에 차가 설 수 없다 (V3)
- 결과는 `served`·`unserved`·`censored` 중 하나이고 합이 전체 인원이어야 한다 (V8)

### ② 재계산 — 엔진과 다른 방법으로 다시 돌린다

같은 입력을 받아 **구조가 다른 방식으로** 시뮬레이션을 다시 돌리고 승객 단위로 비교한다.
구조를 일부러 다르게 하는 이유는, 같은 자료구조를 쓰면 같은 실수를 반복하기 때문이다.

| | 엔진 | 검증기 |
| --- | --- | --- |
| 승차 대기 | 정류장·목적지별 FIFO 대기열의 머리를 k-way 병합, 지연 삭제 | **대기열 없음.** 사건 키를 전부 만들어 한 번 정렬 |
| 승차자 선정 | 대기열에서 꺼냄 | 매번 **전체 승객 선형 탐색** 후 정렬 |
| 일정 표현 | 운행편별 `(stops, arrivals, departures)` 튜플 3개 | **방문(Visit) 평면 목록** |
| 지표 | 실행 중 누적 | 재계산 결과에서 **사후 계산** |

승객 발생도 다시 만든다(V1). 엔진의 생성기 코드를 보지 않고 명세 문장만 보고 구현해,
집계 수요와 seed로부터 같은 승객·같은 체크섬이 나오는지 확인한다.

### ③ 손계산 대조 — 사람이 푼 답

정답의 최종 출처는 **사람이 손으로 계산한 표**다(명세 §5). 그 표를 `handcalc/*.json`에
옮겨 두고, 검증기의 재계산이 그 값과 맞는지 확인한다.

옮길 때의 규칙: **명세가 말하지 않은 값은 넣지 않는다.** 엔진 출력을 보고 채우면 그 순간
정답이 엔진 출력이 되어 버린다. 그래서 비어 있는 항목은 "검증 대상이 아님"이 아니라
"명세 미기재"다.

### 정답으로 쓰지 않는 것

- **엔진 출력** — 검증 대상이지 정답이 아니다.
- **엔진의 golden 로그**(`tests/sim/golden`) — 엔진이 만든 것이므로 회귀 기준일 뿐이다.
  "예전과 같다"는 "맞다"가 아니다.
- **엔진을 호출해 얻은 값** — 검증기는 엔진을 import하지도, 실행하지도 않는다.

### 검사가 공허하지 않다는 것을 어떻게 아는가

통과만 하는 검사는 쓸모없다. 그래서 **정상 산출물을 한 군데씩 고친 사본**을 만들어
해당 검사가 실제로 잡는지 확인한다(명세 §6의 T1–T20). 자세한 것은 §변조 검출.

## 재계산 oracle의 탐색 방식

구조를 엔진과 다르게 둔 이유는 §방법론 ②에 있다. 구현에는 선택지가 둘이다.

| `scan` | 방식 | 쓰는 곳 |
| --- | --- | --- |
| `full` (기본) | 승차마다 **전체 승객 선형 탐색**. 명세 §4 문장 그대로다 | 기본값 |
| `index` | 출발 정류장으로 후보를 먼저 가른다. 상태·목적지 판정과 정렬은 그대로 선형이며 대기열이 아니다 | 큰 규모 |

두 방식이 같은 결과를 내는지 테스트로 고정한다. 다르면 `index`가 조건을 잘못 줄인 것이다.

## 변조 검출 (명세 §6)

T1–T20을 표로 두고 각 사례가 명세가 적은 검사에 걸리는지 확인한다. 같은 사례를 두 번
돌린다.

1. 그대로: 파일을 건드리면 V17(체크섬)이 무조건 걸린다.
2. `tamper.repair_digests`로 manifest·measurement의 digest를 다시 맞춘 뒤: V17의 도움
   없이도 해당 검사가 잡아야 한다. 이쪽이 실제 검출력이다.

명세 §6의 "기대 검출" 중 실제로 걸리지 않는 것은 `Case.not_caught`에 사유와 함께 남긴다.
조용히 지우지 않고 테스트로 고정해 둔다(T5의 V9, T6의 V2).

## 명세와 다르게 구현한 곳

- **V2**: 명세는 키 `(time_s, phase, stable_id)`가 "엄격 증가"라고 적었으나 실제 엔진 출력은
  같은 키에 사건이 여럿이다(한 방문의 하차 여러 건 + 도착 1건, 한 방문의 승차 여러 건).
  명세 §2 자신이 "같은 키에서 alighted가 먼저"라고 적어 엄격 증가와 모순한다. 여기서는
  **약한 증가 + phase 0·2에만 중복 허용 + phase 0 내부 순서(alighted 먼저, vehicle_arrived
  최대 1회) + phase 1·3·4 키 유일**로 검사한다. 엔진을 통과시키기 위한 완화가 아니라,
  명세대로는 모든 정상 출력이 실패하기 때문이다.
- **정수 검사**: 명세 V2의 "정수" 조건은 파일을 읽는 시점에 `InputError`로 걸린다. 검사
  위반이 아니라 입력 오류로 보고된다.
- **M2 사유와 기한 종류 구분**: 명세 §5 표의 "사유"는 M2 사유(`no_connection`·`service_end`·
  `journey`·`wait`)이고 일정 전체를 봐야 정해진다. 사건 로그만으로는 기한 종류(`wait`·`journey`)
  밖에 알 수 없다. 그래서 V8은 `served`·`unserved`·`censored`까지만 판정하고 사유는 V10에서
  다룬다.

- **V1 생성기**: 명세의 `base = SHA-256(json.dumps([generator, seed, aggregate_id]) ‖ \0)`가
  중의적이다. base를 32바이트 digest로 읽으면(A) 합성 complex 1천 명 중 3명만 맞고, 해시
  입력의 앞 바이트열로 읽으면(B) 1000명이 맞는다. (B)로 구현했다. 명세에 "`SHA-256(base ‖
  index ‖ c)`의 base는 digest가 아니라 앞 바이트열"임을 명시해야 한다.
- **V15 운행편 1개 노선**: 연속 출발이 없는 노선의 "최대 간격"을 명세가 정의하지 않았다.
  엔진은 그 노선을 `max_gap_by_route_s`에서 생략한다. 검증기는 간격이 정의되는 노선만
  비교하고 생략된 노선을 note에 남긴다. 어느 쪽으로도 맞추지 않았다.
- **V16은 통과하지 않는다**: R10(가용 fleet 대수)은 `Scenario.fleet`이 산출물에 없고,
  R13(방향별 구간)은 명세 §3이 직접 "미검증(통과 아님)"으로 정했다. 검사 가능한 R11 정원·
  R14 운영창·차량 duty 비중첩·출발 거점 일치에 위반이 없어도 상태는 `not_verified`다.
- **V14 하차 순서**: 한 방문에서 여러 명이 내릴 때의 순서를 명세가 정하지 않았다. 재계산은
  승차 순서로 내린다. 지표에는 영향이 없으나 로그 바이트 비교에는 영향이 있다.
- **명세 §4 규모 상한**: 명세는 1만 명 초과에도 V11(만차 거절)을 적용한다고 적었으나,
  V11은 재계산 oracle 없이는 판정할 수 없다(§4가 oracle을 N ≤ 10,000으로 한정한다).
  상한을 넘으면 V6·V7·V9–V14를 `not_run`으로 남긴다. V11도 거기 포함된다.
